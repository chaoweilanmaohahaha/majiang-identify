# 设计：上海敲麻胡牌识别核心模块

## Context

仓库目前只有 uni-app（Vue3 + Vite + TS）脚手架，`src/` 下无业务代码。本变更新增纯 TypeScript 算法模块，不依赖小程序运行时，可直接用 vitest 测试，也便于后续其他麻将变种复用。动机见 proposal.md。

## Goals / Non-Goals

**Goals:**
- 建立可复用的牌编码与手牌输入结构，作为后续变种的基础。
- 实现胡牌判定、类型识别、听牌判定三个纯函数，行为与 spec.md 一致。

**Non-Goals:**
- 不做"听牌必须敲"的流程校验与对局状态机（后续 feature）。
- 不做番数/得分计算、页面 UI。

## Decisions

### 1. 牌编码：0-41 的整数
- 0-8：一万~九万；9-17：一条~九条；18-26：一筒~九筒；27-30：东南西北（可组合牌共 31 种）。
- 31-33：红中、发财、白板（上海敲麻中按花牌处理）；34-41：春夏秋冬梅兰竹菊（花牌共 11 种）。
- 理由：计数数组（length 42）索引即编码，判定算法性能最好、代码最简。
- 备选：字符串编码（"1m"）可读性好但需映射层，判定时反而多一步转换，不采用。

### 2. 输入结构（`HandInput`）
```ts
interface Meld {
  tiles: TileId[]      // 3 张：吃/碰；4 张：杠（含暗杠）
  kind: 'chi' | 'peng' | 'gang'
}
interface HandInput {
  concealed: TileId[]  // 暗牌
  melds: Meld[]        // 副露，可为空
  flowers: TileId[]    // 花牌（已杠出，只记录）
}
```
- 折算张数 = `concealed.length + 3 × melds.length`（杠也是 1 个面子）。
- 胡牌判定要求折算 = 14 且 `concealed.length ≡ 2 (mod 3)`；听牌判定要求折算 = 13 且 `concealed.length ≡ 1 (mod 3)`；同种牌（暗牌+副露）合计 ≤ 4；花牌编码须在 31-41（31-33 为红中/发财/白板，34-41 为八种季节/花朵牌）。违反即抛输入错误。
- 杠（含暗杠）统一要求以副露形式输入；暗牌中若出现 4 张相同牌，判定算法仍能处理（可拆为刻子 + 单张参与顺子/将）。

### 3. 胡牌分解：回溯 + 按计数递归
- 先把每个副露记为 1 个固定面子（顺子或刻子，杠按刻子处理），再从暗牌计数数组递归：优先取对子，再取顺子或刻子。
- 递归返回完整分解结构（不单是布尔值），供类型识别复用。
- 暗牌 ≤ 14 张，最坏情况量级极小，无需记忆化；但仍按计数数组组织避免对象分配。

### 4. 类型识别：按类型各自搜索满足条件的分解
- 门清平胡：`melds` 为空 且 存在"四个面子全为顺子"的分解（将牌不限）。
- 碰碰胡：存在"四个面子全为刻子"的分解（杠计入刻子）。
- 清一色：暗牌+副露全部为同一花色的数牌（无风牌）。
- 混一色：至少含一张风牌（东南西北），且非风牌全部为同一花色（红中/发财/白板属花牌，不参与类型判定）。
- 返回全部命中的类型（位标志或数组），未胡牌返回空。
- 理由：同一手牌可能存在多种拆法，按类型独立搜索"是否存在满足条件的分解"最直接、不易漏判叠加类型。

### 5. 听牌判定：31 种补牌逐一验证
- 对 31 种数牌/风牌逐一：若补入后不超 4 张且构成胡牌，则记为听口。
- 输出升序听口列表；不包含花牌（含红中、发财、白板）。复杂度 31 × 一次分解，可接受。
- 备选：增量剪枝的听口算法复杂且易错，先以穷举实现，实测性能足够（每个候选 14 张分解）。

### 6. 模块位置与文件划分（纯 TS，位于 `src/core/mahjong/`）
- `tile.ts`：编码常量、花色/数字/风牌/花牌（含红中/发财/白板）判定、`tileName(id)`。
- `types.ts`：`TileId`、`Meld`、`HandInput`、`HuType`（门清平胡/碰碰胡/清一色/混一色）、错误类型。
- `decompose.ts`：胡牌分解算法（供 win/type/listen 复用）。
- `judge.ts`：`isWinningHand(input): boolean`、`getWinTypes(input): HuType[]`。
- `listen.ts`：`getListeningTiles(input): TileId[]`。
- `index.ts`：统一导出。
- 理由：小程序页面后续只 import `index.ts`；`decompose` 独立便于变种复用。

### 7. 测试：vitest（devDependency，`vitest@^1.6`，兼容 Vite 5）
- `package.json` 增加 `"test": "vitest run"`。
- 测试文件与被测模块同目录（`*.test.ts`），覆盖 spec.md 全部场景，另加边界（全刻子拆法、杠、超四张、非法编码、听口去重）。
- 备选：jest 需额外配置 ts-jest，与 Vite 生态不协调，不采用。

## Risks / Trade-offs

- [敲麻具体规则存在各地差异（如平胡将牌限制）] → 类型判定相互独立、规则常量集中定义，后续按需调整不影响主判定。
- [穷举听口性能] → 单次判定数据量固定（≤14 张），无性能风险；若未来加算番变复杂，再引入缓存/剪枝。
- [vitest 引入后 `npm run type-check` 范围扩大] → 测试文件同样纳入类型检查，属期望行为；`npm run build:mp-weixin` 不会把测试文件打进产物（未被 import）。
